📚 Technical Documentation
System architecture, integrations, and deployment reference for anyone supporting or maintaining this platform. Visible to admins.
Overview
RawTalent HeartBeat is a single Node.js/Express application serving both the public-facing staff site (search, Ask AI, FAQ, glossary, announcements, team directory, training) and the internal admin panel (content management, call quality, workforce management, projects, user administration). It's a monolith by design — one server process, one Postgres database, no microservices or separate frontend build step.
Tech Stack
Backend: Node.js + Express 4. Sessions via express-session with a custom Postgres-backed session store (services/sessionStore.js), auth via Passport (local email/password + Google OAuth).
Database: Postgres, hosted on Supabase (session pooler connection). Accessed through a small wrapper in db/database.js that exposes a single getDb().execute({ sql, args }) call — ? placeholders are translated to Postgres $1, $2… under the hood. This wrapper is a holdover from an earlier SQLite/Turso version of the app and is intentionally not meant to be extended further — new queries should move toward native pg usage over time.
File storage: Supabase Storage (private buckets, signed URLs only — team photos, article attachments, call recording audio, project SOP files, announcement attachments).
Frontend: No framework, no build step. Plain HTML/CSS/vanilla JS — public/index.html (public KB) and public/admin.html (admin panel) are each a single large file with inline <script>. Styling is one shared stylesheet, public/css/style.css.
AI: Anthropic Claude API (@anthropic-ai/sdk) powers Ask AI, FAQ candidate classification, call grading, meeting Q&A, and report generation.
Deployment: Railway — project rawtalent-knowledgebase, service web, production environment, deployed automatically from the GitHub repo on every push to main. Live at rawtalent-internal.app. (The fly.toml/Procfile in the repo root are unused leftovers from an earlier, abandoned Fly.io setup — Railway ignores them and auto-detects the Node app on its own. Safe to delete, just hasn't been cleaned up yet.)

Authentication & Roles
Sessions are cookie-based (Passport + express-session), stored server-side in Postgres so they survive redeploys. Sign-in is email/password or Google OAuth. Roles are enforced on every API route server-side (client-side nav hiding is cosmetic only):
user — public site only, no admin panel access.
qa_view — a narrow admin role: Articles (view/add/edit, no delete), Glossary (view/add/edit, no delete), Leads and the WFP Dashboard (both view-only), FAQ Review (add/edit approved FAQs only), and Call Quality (Dashboard/Rubrics/Evaluator). See the Role Permissions page for the full breakdown.
workforce_partner — for external Workforce Partners (Gwen, Justine, Liam): the same base set as qa_view (Articles, Glossary, FAQ Review, Call Quality — see qa_view above), plus Leads (view all, edit only Position/Contact Name/Email, add their own notes, add centres — status/assignment editing stays admin/super_admin only), the WFP Dashboard, and Route Planner. Newer role, still being shaped — expect individual items to change. See the Role Permissions page for the full breakdown.
admin — full admin panel access.

Key Feature Areas
Content & Search: full-text article search (Postgres tsvector), Ask AI (Claude, grounded in articles + AI Sources), Glossary, Announcements, Team directory, Training.
FAQ Review: scans Slack and Fathom for reusable Q&A content, classifies candidates with Claude, holds them for human approval before they become live FAQs.
Call Quality: syncs recordings from Dubber, grades them against a configurable rubric (AI or manual), calibration notes, and period reports.
Workforce Management: live agent presence (Webex), background-polled every 20s independent of who has the page open; Detailed Call History dashboard (volume, answered/missed rate, average handle time) once the org has Webex Calling licensing.
Training: course builder, assignment, attempts/scoring.
Projects: internal project tracking with milestones and SOP file attachments.
Meetings: Fathom transcript archive with Claude-powered Q&A across all past meetings — a private, restricted-access area.
Deployment
Hosted on Railway — project rawtalent-knowledgebase, service web, production environment, live at rawtalent-internal.app. Deployed straight from the GitHub repository (rawtalentintra/rawtalent-intranet) — every push to main triggers a new deployment automatically. There's no separate build step — it's plain Node.js, started via node server.js. The database schema in db/schema.sql applies automatically on boot. Environment variables (the ones listed above) are configured in the Railway service's Variables tab, not committed to the repo — .env is git-ignored and only used for local development.
Local Development
Clone the repo, copy .env.example to .env and fill in at least the Supabase and admin-account variables (everything else is optional), then npm install and npm start (or npm run dev for auto-restart via nodemon). The app runs on http://localhost:3000 by default.
🗂️ RT API Data Reference
Every field the RtApiReport API (behind Reports) actually returns, verified against its live swagger.json — not just what's currently shown in the Reports dashboard. Super admin only, personal reference.
🎉 Worth knowing: this API grew since Micropods was shelved
When Micropods was scoped, the Candidates and Clients endpoints exposed no address, qualification, or availability data at all — that's why it was shelved. Re-checking the live schema for this reference turned up that the API has since grown: CandidateResponse now includes addresses[] (with pre-geocoded latitude/longitude), qualifications[], and availableCandidateList[]; ClientResponse now includes locations[] (also pre-geocoded). The specific blocker for Micropods no longer applies as-is — worth a fresh look if that feature comes back up. See the Candidates and Clients tables below for exactly what's in each.
How to read this
✓ Clear the field's name and type tell you exactly what it is — safe to use directly.
⚠ Vague code a raw numeric ID or status code with no lookup table exposed anywhere in the API — the number means something, but the API doesn't say what. Only way to resolve these is to ask RawTalent's original developers for the code tables, or reverse-engineer meaning by cross-checking known real records against what you'd expect.

🔬 Live data sweep — RT API now connected to the real production database
Once the dev team pointed this API at the live database, most of the "vague code" fields above stopped being unknowable — pulling real samples (1,000–1,600 records per type, mixing oldest and newest) and cross-referencing values against other fields on the same records resolved several of them outright, and gave strong evidence for several more. Two confidence tiers, marked directly on each field below:
🔬 Confirmed — an ID and its human-readable label appear together in the same real record (e.g. a qualification's qualificationId and qualificationName on the same object) — this is as reliable as reading it straight from documentation.
🔬 Inferred — no label exists anywhere, but the value's behavior across hundreds of real records makes the meaning very likely (e.g. a booking status that's always paired with an assigned candidate and a past date). Strong evidence, not a guarantee — still worth a quick confirmation from the dev team before anything depends on it being exactly right.
Two things came out of this sweep that aren't code-labeling issues at all, worth flagging separately: Timesheets' duration field is 0 in every one of 1,000 sampled records — looks unpopulated/unused by the source system, so actual worked hours should be computed from endTime − startTime instead. And isPaid/isInvoiced were false in all 1,000 sampled records regardless of status — worth asking the dev team directly whether those two fields are actually being written to at all.

Same exercise again, checked against the live Clients/Client Visits/Service Provider screens. Our Clients report currently treats each ClientResponse as a row; matching this view means iterating locations[] instead.

Best-fit hypothesis: 1 = Open (never assigned, always future), 2 = Requested (assigned, mostly future, rare), 3 = Assigned (always assigned, mostly future), 5 = Completed (always assigned, always past — the dominant value), 6 = Cancelled (mixed assigned/unassigned, mixed past/future), 7 = Failed/Unfilled (never assigned, always past). Don't assume it's the same table without confirming.
